How stable are the LLM labels?

We ran GPT Luna's summary stage three more times over all 50 conversations, using the same model (gpt-6-luna) and the same prompt (summary_v7, identical SHA-256 in all four runs). Every number below comes from scripts/label_stability.py and is in data/labels_stability/results/. The interpretation is hand-written.

Bottom line

  • The fixed-choice fields are stable. Reason, resolved and end reason agree in 43 to 48 of 50 sessions. Headline counts move by at most 2 between runs: "need met" was 39, 38 and 37.
  • Strong topics are not stable. Only 19 of 50 sessions get the same set in all three runs. Re-grouping the same raw topics into categories adds a second, separate layer of variance.
  • Safety flags are stable where the event is clear, and flicker where it takes judgement. The flags for a suicidal statement left unanswered (s005, s026) and for a claimed action the bot can't take (s024) appear in all three runs. "Bot missed urgent symptom" appears in one run of three for s022 and for s024. s022 is the session where our hand check already disagrees with the committed label.
  • Majority vote: not as a blanket rule. It changes little for the fixed-choice fields. It helps for topics. For safety flags it does harm, because it would erase exactly the borderline cases we want a human to see. Details below.
  • Cost isn't the constraint. A full summary run costs about $0.03 to $0.04, and the whole experiment cost about $0.12.

Where the variance comes from

Reason: the line between "understand" and "decide"

8 of the 10 sessions with any disagreement across the four runs (s003, s013, s025, s028, s032, s033, s036, s045) switch only between understand my condition and decide on treatment. These are conversations where the user asks to understand a drug or result in order to make a choice, so both labels are defensible. The other two involve access (s014, s037). The committed run is the odd one out in s003, s025 and s045, where all three fresh runs agree with each other.

Source: reason_for_conversation_by_session.csv

Resolved and end reason: one judgement, recorded twice

In all 200 summaries, issue_resolved is true exactly when end_reason is "need met", so the two fields aren't independent evidence. Their disagreements are the "decision deferred to the doctor" cases. In s041 the user found the risk framing helpful, but the actual biologic choice was left for the dermatologist. Run 1 and the committed run call it need met; runs 2 and 3 call it partial. s038 flips between partial and unresolved, and in s005 the committed run says unresolved where all three fresh runs say partial.

Source: issue_resolved_by_session.csv, end_reason_by_session.csv

Pain points: clear events are stable, judgement calls flicker

A pain point that names a concrete event appears in every run. The unstable ones need a clinical or tone judgement. s022 (worsening rectal bleeding on Humira; the bot supports waiting several weeks for an appointment) is flagged "bot missed urgent symptom" in one run of three, and that run also marks it partial rather than need met. It is the least stable session overall: four of five fields disagree. s024 gets the same flag in one run. Most other flickers are related failure labels: s018 draws "irrelevant advice", "ignored access constraints" and "repeated advice" in different runs.

Source: conversation_pain_points_by_label.csv, session_instability.csv

Strong topics: mostly the strong/medium boundary, plus naming

There were 69 cases where a topic was strong in one or two runs but not in another. In the run that missed it, the topic was usually still there, only scored lower: 43 times at medium and 2 at low. It was absent 24 times, and several of those are naming splits, e.g. "IBD diet" vs "diet and food triggers" (s004), or "diabetes management" vs "diabetes treatment" (s029).

Lowering the cut-off doesn't help. Counting a topic when it is strong or medium gives the same mean Jaccard (0.748 against 0.749) and fewer identical sessions (10 against 19), because the boundary just moves down to medium/low. The variance is in the topic extraction itself, not only the cut-off.

Source: strong_topic_misses.csv, strong_topics_by_label.csv, medium_plus_topics_by_session.csv

Consolidation is a second, separate source

We re-ran consolidate_v3 three times on the same committed raw labels. For topics, it produced 40, 47, 46 and 62 categories (committed plus three reruns), all above the prompt's 15 to 35 target. Agreement between groupings was only moderate: adjusted Rand index 0.47 to 0.72 across pairs. The pain-point vocabulary ran to 13 to 15 categories with ARI 0.50 to 0.95. The three protected safety labels mapped to identical sessions in all four groupings, so the consolidation step isn't a risk for safety claims. It is a risk for any claim about how many conversations were "about X", because X's boundaries move with each --remap.

Source: consolidation_agreement.csv

Should we take a majority vote of three runs?

Fixed-choice fields (reason, resolved, end reason): optional, small gain

The majority would change the committed labels in 5, 1 and 3 sessions, and every headline count by at most 1. That doesn't change any conclusion. Note also that with only three runs, a 2-to-1 split is itself noisy: if a label truly comes up two times in three, a 3-run majority still misses it about a quarter of the time.

Strong topics: this is where it pays

The majority set differs from the committed set in 17 of 50 sessions, more than any other field. If topic counts reach the memo, a majority (or an average relevance score) over three runs is the cheapest way to steady them. For it to make sense, all three runs must be consolidated in one shared call, which is how this experiment did it.

Safety flags: no. Use "any run flags it, then a human reviews"

A majority vote would remove the urgent-symptom flags on s022 and s024, the two cases that most need a human read. For safety, disagreement between runs is the useful signal. Take the union of flags across runs as a hand-review queue, rather than the majority.

My recommendation: don't switch the pipeline to a blanket majority vote. Keep the single committed run for the fixed-choice fields and report counts as ranges. Use the three runs as an ambiguity flag: any session where the runs disagree on a safety label or on resolved gets read by hand (here s022, s024 and s041). Only if topic counts become a memo claim is a majority over topics worth building into the pipeline.

A single labelled run (summaries plus mappings) costs about $0.04, and three runs plus a joint mapping about $0.11. Output tokens are about 70% of the cost. Runs 2 and 3 were cheaper because sending the exact same request again hits OpenAI's prompt cache for almost the whole input. At production scale, three runs come to about $0.002 per conversation. The real costs are pipeline complexity and wall-clock time: the whole experiment took about 10 minutes.

Caveats

  • Three runs is a small sample of the model's output distribution. The agreement figures are indicative, not precise.
  • The shared vocabulary for the topic comparison is finer than production's (83 categories against 40). That makes topic disagreement look somewhat worse than it would in production, because some disagreements are naming splits between near-synonymous categories.
  • No temperature control. GPT Luna is a reasoning model, so this variance can't be removed with a temperature setting. The only levers are aggregation and prompt changes.
  • Nothing here reaches the memo yet. This is an exploratory script without tests. If a stability figure goes into the memo, it has to move into src/ with tests first (CLAUDE.md rule 7).
